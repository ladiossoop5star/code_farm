# 把重複操作交代給 AI

[English](prompts.en.md)

先準備一個獨立的測試目錄，放入可修改的假資料副本。把輸入、預期輸出和錯誤情境寫進需求，用便宜的模型先試一輪。可以把這段加到下面任一份提示的開頭。

> 請在這次的測試目錄內工作，只使用我提供的範例和需求。實作後各跑一次正常與錯誤情境，回報實際輸出、退出碼，以及產生或修改了哪些檔案。

## replace-text

> 我每次都要在一份設定檔裡替換 log 路徑。請做一個叫 replace-text 的指令，依序接收檔名、舊文字和新文字。檔名可能含有空白，兩個值可能含斜線。照字面找，保留原換行格式，印出改過的行號和內容。用 test profile.conf 的 ./logs/staging → ./logs/run-01，以及 smoke profile.conf 的 ./logs/smoke → ./logs/run-02 驗證。

## dut-ip

> 我的 DUT 平常沒接螢幕。IP 換掉時，我想用先前記下的 MAC 找回位址。請做一個叫 dut-ip 的指令。給它 MAC 和網卡，就用 arp-scan 查這張網卡所在的 IPv4 區網，然後印出完整匹配這個 MAC 的所有 IPv4。允許用 --from 讀已保存的掃描結果。用改 IP 前後的兩份回應驗證，也測試沒有匹配和掃描失敗的情況。

## wait-ready

> 測試開跑前，我要反覆執行現成的就緒查詢。請做 wait-ready，雙減號之前是查詢間隔和最長等待時間，之後是一條完整指令和它的參數。查詢回 0 表示就緒，1 表示繼續等，其他值表示查詢失敗。查詢本身卡住也受同一期限約束。輸出 READY、TIMEOUT 或 QUERY_ERROR，外層分別拿到 0、124 或 2。用延遲就緒、從未就緒、查詢回錯及卡住的四種情況驗證。

## snap-log

> 我每輪測試後都把 log 複製到另一個目錄，再找失敗行。請做 snap-log，我提供原始 log 和輸出目錄。每次建立一個新的子目錄，保留原始 log 並另寫帶原始行號的失敗摘要。範例用 DUT SELFTEST FAIL: 這個行首當失敗條件。用同一份範例跑兩次，確認子目錄不同，並用 cmp 確認每份原始檔和輸入完全相同。

## 接回測試流程

> 用設定檔裡的輸出路徑跑一輪本機測試。先用 wait-ready 等就緒，再執行自測。把等待和自測的輸出寫進同一份 log，最後用 snap-log 保存。驗證自測通過、自測失敗和等待逾時。逾時不要執行自測，三種情境各自留 log，保留適當的退出碼。再驗證查詢指令直接回錯的情況。
